WESCOMM QA AND STAGING RUNBOOK
Last updated: July 11, 2026

PURPOSE
This runbook verifies the student, staff, and admin experiences without changing
live inventory. Browser automation covers browsing, local cart behavior, login,
logout, and role-based API access. Checkout, inventory writes, email OTP, push
delivery, and database recovery remain controlled manual checks on staging.

4. CONTROLLED STAGING TESTS THAT CHANGE DATA
============================================================

Use a separate staging Supabase project or clearly named QA products. Do not run
these checks against final production inventory.

Student reservation lifecycle:
1. Record the QA product's starting stock.
2. Student reserves one item.
3. Confirm stock decreases exactly once.
4. Double-click/retry the same checkout and confirm no duplicate reservation or
   second stock deduction is created.
5. Staff moves PENDING -> CONFIRMED -> READY_FOR_PICKUP -> COMPLETED.
6. Confirm the student receives in-app and push updates at each relevant state.
7. Repeat with cancellation and confirm stock is restored exactly once.
8. Attempt an invalid status jump and confirm the API returns 400.

Concurrent last-stock check:
1. Create a QA product with exactly one available item.
2. Use two different student accounts/devices.
3. Submit both reservations at nearly the same time.
4. Exactly one request must succeed.
5. The other must receive a stock conflict; stock must never become negative.

Inventory management:
1. Staff creates a QA product with an image and variants.
2. Edit price, available quantity, and staff attention level.
3. Confirm the student Shop updates without a hard refresh.
4. Restock using both Add quantity and Set exact quantity.
5. Archive the QA product and confirm it disappears from the public Shop.
6. Confirm every write appears in Admin Audit Logs.

Support privacy:
1. Create conversations from two separate student accounts.
2. Each student must see only their own threads.
3. Staff/admin can see operational threads according to their role.
4. Confirm typing indicators and new messages update without manual refresh.
5. Inspect the database and confirm encrypted support fields do not contain the
   original plaintext.

5. PHONE AND BROWSER PUSH CHECK
============================================================

1. Use HTTPS staging. Localhost is acceptable only for desktop development.
2. Log in on the phone and enable Phone notifications in Account Settings.
3. Accept the browser permission prompt.
4. Close or background WESCOMM.
5. Change a reservation to Confirmed, Ready for pick-up, then Completed.
6. Confirm a push appears for each expected event.
7. Tap the push and confirm it opens the correct WESCOMM page.
8. Disable notifications and confirm the subscription is revoked.

On iPhone/iPad, install WESCOMM to the Home Screen before testing web push.
Browser private/incognito mode is not a reliable push-notification test.

============================================================
7. BACKUP AND RECOVERY CHECK
============================================================

Before schema changes or a release:
1. Create a database backup/export and record its UTC timestamp.
2. Store it outside the application repository.
3. Back up DATA_ENCRYPTION_KEYS separately in a secure offline location.
4. Restore the database into a temporary Supabase/PostgreSQL project.
5. Run Prisma generate and GET /api/health/ready against the restored database.
6. Verify encrypted profile/support fields can still be read by the application.
7. Delete the temporary restore only after verification.

The database backup is not sufficient without the matching encryption key set.
