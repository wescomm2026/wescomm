WESCOMM QA AND STAGING RUNBOOK
Last updated: September 1, 2026

PURPOSE
This runbook verifies the student, staff, and admin experiences without changing
live inventory. Browser automation covers browsing, local cart behavior, login,
logout, and role-based API access. Checkout, inventory writes, email OTP, push
delivery, and database recovery remain controlled manual checks on staging.

4. CONTROLLED STAGING TESTS THAT CHANGE DATA
============================================================

Use a separate staging Supabase project or clearly named QA products. Do not run
these checks against final production inventory.

Student reservation lifecycle:
1. Record the QA product's starting stock.
2. Student reserves one item.
3. Confirm stock decreases exactly once.
4. Double-click/retry the same checkout and confirm no duplicate reservation or
   second stock deduction is created.
5. Staff moves PENDING -> CONFIRMED -> READY_FOR_PICKUP -> COMPLETED.
6. Confirm the student receives in-app and push updates at each relevant state.
7. Repeat with cancellation and confirm stock is restored exactly once.
8. Attempt an invalid status jump and confirm the API returns 400.

Concurrent last-stock check:
1. Create a QA product with exactly one available item.
2. Use two different student accounts/devices.
3. Submit both reservations at nearly the same time.
4. Exactly one request must succeed.
5. The other must receive a stock conflict; stock must never become negative.

Inventory management:
1. Staff creates a QA product with an image and variants.
2. Edit price, available quantity, and staff attention level.
3. Confirm the student Shop updates without a hard refresh.
4. Restock using both Add quantity and Set exact quantity.
5. Archive the QA product and confirm it disappears from the public Shop.
6. Confirm every write appears in Admin Audit Logs.

Support privacy:
1. Create conversations from two separate student accounts.
2. Each student must see only their own threads.
3. Staff/admin can see operational threads according to their role.
4. Confirm typing indicators and new messages update without manual refresh.
5. Inspect the database and confirm encrypted support fields do not contain the
   original plaintext.

September operational feature acceptance:
1. Create a closure preview containing AUTO_RESCHEDULE and NEEDS_REVIEW rows.
2. Activate once and confirm eligible reservations move once, capacity is
   honored, history records SYSTEM_CLOSURE, and students are notified.
3. Repeat the activation request with the same idempotency key and confirm no
   second move or duplicate notification occurs.
4. Scan one receipt token as guest, owner, Staff, and Admin. Confirm public data
   stays masked, owner navigation opens only the owned receipt, Staff/Admin use
   the internal receipt record, and scanning alone never verifies a receipt.
5. Search Students by name, student number, and email. Confirm operational tabs
   are paginated and identity/role/authentication fields remain read-only.
6. Resolve, archive, restore, and edit a latest human message. Confirm the
   encrypted revision and Edited indicator remain visible after refresh.
7. As Admin, move an operations-archived conversation into retention. Confirm
   Student and Staff can no longer access it, then restore it successfully.
8. Permanent purge must stay locked until 90 days have elapsed. On an eligible
   fake conversation, request a fresh preview, enter the exact phrase, purge,
   and confirm only the PII-free audit tombstone remains.

sandbox database. Never use this CI bootstrap against staging or Production;
Supabase already manages those roles.

============================================================
10. ROLLOUT AND ROLLBACK RULES
============================================================

Rollout order:
1. Record backup timestamp and migration status.
2. Apply and verify additive migrations during a low-traffic window.
3. Deploy backend and frontend from the same reviewed commit.
4. Check readiness, authentication, core reads, then the Phase 1-8 smoke flows.
5. Monitor request IDs, audit logs, outbox/notification health, and errors.

Rollback rules:
- Do not manually reverse or edit an applied Prisma migration.
- If application code is unhealthy but database integrity is good, roll back the
  application deployment and keep the additive schema in place.
- A code rollback does not reverse automatic pickup moves. Use preserved
  schedule history and approved manual correction; do not move records backward
  automatically.
- Permanent conversation purge is irreversible in the application. Test it only
  with fake staging evidence. Recovery of real purged data would require an
  approved whole-database backup restore and may overwrite newer data.
- Restore a database backup only for confirmed data/schema corruption, with an
  owner-approved maintenance window and a documented recovery point.
- After any rollback, rerun migration verification and GET /api/health/ready,
  then record the incident, request IDs, affected records, and final decision.
