1. RULES BEFORE TESTING
============================================================

[ ] Use only the staging deployment and designated test accounts.
[ ] Do not enter real student personal information.
[ ] Prefix temporary records with QA, for example: QA Test Product.
[ ] Record the starting stock before testing checkout, cancellation, or restock.
[ ] Do not delete records created by another tester without permission.
[ ] Capture a screenshot or short screen recording for every confirmed defect.
[ ] Retest a fixed defect using the same steps before marking it Passed.
[ ] Test on a normal browser window. Use Incognito only for clean-session tests.
[ ] Do not run destructive database commands against production.

SEVERITY GUIDE

- Critical: Data leak, account takeover, unauthorized admin access, lost or
  corrupted inventory, or the whole system is unavailable.
- High: Login, checkout, reservation, staff inventory, or another main workflow
  cannot be completed.
- Medium: A feature works incorrectly but has a workaround.
- Low: Visual, wording, alignment, spacing, or minor usability issue.

============================================================
5. CHERRY - SECURITY AND PRIVACY QA
============================================================

IMPORTANT
Perform only authorized, non-destructive testing against WESCOMM staging. Do not
run denial-of-service tools, automated password attacks, or destructive SQL.

A. SESSION AND CREDENTIAL SECURITY

[ ] Production login uses Supabase verification/password authentication.
[ ] Session cookie name is __Host-wescomm_session.
[ ] Cookie has HttpOnly, Secure, SameSite=Lax, and Path=/.
[ ] No Supabase access token is stored in Local Storage or Session Storage.
[ ] Password and OTP fields are masked or handled appropriately.
[ ] OTP cannot be reused after successful verification.
[ ] Expired OTP returns a safe error.
[ ] Logout invalidates the server session.
[ ] Closing/reopening the browser follows the intended remember-session policy.
[ ] Development login endpoint is disabled in production.

B. ROLE-BASED ACCESS CONTROL

[ ] Guest cannot access student-private, staff, or admin APIs.
[ ] Student receives 403 from every staff and admin API.
[ ] Staff receives 403 from admin-only users and audit-log APIs.
[ ] Admin can access authorized admin APIs.
[ ] Manually entering a staff/admin URL does not bypass authorization.
[ ] Changing a role value in browser storage does not grant access.
[ ] Backend authorizes every protected action, not only the frontend UI.

C. OBJECT-LEVEL PRIVACY AND IDOR TESTS

[ ] Student A cannot read Student B reservations by changing an ID.
[ ] Student A cannot read Student B receipts by changing an ID.
[ ] Student A cannot read or post in Student B support conversation.
[ ] Student cannot mark another user's notification as read.
[ ] Uploaded private/account content is not exposed through predictable IDs.
[ ] Staff access is limited to operational data required by the role.

D. INPUT, FILE, AND API PROTECTION

[ ] Script-like text is displayed as text and never executed.
[ ] SQL-like input does not alter queries or expose database errors.
[ ] Invalid enum, quantity, price, date, and UUID values are rejected.
[ ] Negative quantity and extremely large quantity are rejected.
[ ] Upload rejects unsupported file types and oversized files.
[ ] Uploaded filename cannot change server paths.
[ ] API rejects malformed JSON with a safe 400 response.
[ ] Error messages do not expose stack traces, keys, table names, or SQL.

E. CSRF, CORS, RATE LIMITING, AND HEADERS

[ ] Cookie-authenticated POST/PATCH/DELETE requires the approved origin.
[ ] Cross-origin write request receives 403.
[ ] CORS allows only the configured WESCOMM frontend origin.
[ ] Repeated login attempts trigger the expected rate limit.
[ ] Repeated OTP/session requests trigger cooldown or 429 response.
[ ] Rate-limit response includes safe Retry-After information.
[ ] Content-Security-Policy header is present.
[ ] Strict-Transport-Security is present on production HTTPS.
[ ] X-Content-Type-Options is nosniff.
[ ] X-Frame-Options is DENY or CSP frame-ancestors blocks framing.
[ ] Referrer-Policy and Permissions-Policy are present.

F. DATABASE AND SENSITIVE DATA

[ ] Supabase database rejects non-SSL connections when SSL enforcement is on.
[ ] Sensitive profile phone/address fields are encrypted where configured.
[ ] Support message plaintext is not visible in encrypted database columns.
[ ] DATA_ENCRYPTION_KEYS is not committed to Git.
[ ] Existing encrypted data can still be decrypted after deployment.
[ ] Row Level Security is enabled on direct-access tables where required.
[ ] Push subscriptions cannot be selected directly by anonymous clients.
[ ] Database unique indexes prevent duplicate products, variants, and FAQs.
[ ] Backup and matching encryption keys are stored separately.

G. BUSINESS ABUSE AND AUDITABILITY

[ ] Double-click checkout creates one reservation only.
[ ] Reusing an idempotency key with changed data is rejected.
[ ] Student cannot reserve unavailable or negative stock.
[ ] Student restriction cannot be bypassed by calling the API directly.
[ ] Staff/admin manual restriction actions require a valid reason.
[ ] Admin audit log records product, user, restriction, and receipt changes.
[ ] Audit records identify actor, action, entity, and timestamp.
[ ] Staff cannot delete or alter audit records through available APIs.

H. PUSH NOTIFICATION PRIVACY

[ ] Browser requests notification permission only after a user action.
[ ] Subscription is associated with the authenticated user only.
[ ] Push content does not expose unnecessary private student information.
[ ] Signing out does not expose another user's notification list.
[ ] Revoked subscription no longer receives notifications.

CHERRY DEPLOYED WEBSITE CHECKS

[ ] Open Chrome DevTools on https://wescomm.vercel.app.
[ ] Check Application -> Cookies -> https://wescomm.vercel.app.
[ ] Check Application -> Local Storage and Session Storage.
[ ] Check Network -> select an API request -> Headers and Response.
[ ] Perform role-isolation tests using only the three designated test accounts.
[ ] Record the HTTP status and request ID for every security-related failure.

[ ] Authentication/session security passed
[ ] RBAC and IDOR privacy passed
[ ] Input/upload security passed
[ ] Headers, CORS, CSRF, and rate limits passed
